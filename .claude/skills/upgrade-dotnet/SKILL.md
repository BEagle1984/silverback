# Upgrade to a new .NET LTS

Silverback targets only the latest .NET LTS. A runtime jump goes from one LTS straight to the next, never to an STS in between. It
moves the target framework, the SDK, the runtime-aligned packages and the Renovate holds together, in one change, because each
of them breaks the build or the update flow when it lags behind the others.

Below, `OLD` and `NEW` are the major versions (for example `10` and `12`). Run everything from the repository root in Git Bash.
Use the Edit tool for every change, because the files have CRLF line endings. Ask the user when a decision isn't covered here.

## 1. Settle the version

- Check that `NEW` is a GA LTS release and that a `NEW.0.1xx` SDK is out (`https://builds.dotnet.microsoft.com/dotnet/release-metadata/releases-index.json`: `release-type` is `lts`, `support-phase` is `active`).
  Stop and ask if it isn't.
- Dropping `OLD` is a breaking change for the users. Ask the user which Silverback version ships it, usually the next major. If
  that version isn't the one currently open (the `BaseVersion` in `Directory.Build.props`, with a changelog chapter that has no
  release date yet), run the `start-release` skill first, whatever kind of version it is.
- Check that the SDK is installed (`dotnet --list-sdks`). If it isn't, ask the user to install it.

Done when `NEW`, the exact SDK version (the latest `NEW.0.1xx` patch) and the Silverback version are agreed with the user, that
version is open, and the SDK is installed.

## 2. Inventory

List every place that pins `OLD` (write the command to a script file and run it with `bash`, so that no layer of quoting
changes it):

```shell
OLD=10
git grep -n -I -E "net${OLD}\.0|${OLD}\.0\.x|${OLD}\.0 SDK|\.NET ${OLD}([^0-9]|$)|:${OLD}\.0([^0-9]|$)|\^${OLD}[^0-9]|\"${OLD}\.0\.[0-9]+\"" -- ':!docs/changelog/*' ':!docs/v4/*' ':!*_autogenerated.cs' ':!.claude/skills/upgrade-dotnet/*'
```

The last alternative (a quoted `"OLD.0.<patch>"` version) also lists `global.json` and every package on `OLD.0` in the props
files, held packages included.
Expect at least the places below. The table is a reminder, and the grep output is what step 5 checks against:

| What | Where |
| --- | --- |
| Target frameworks | `DefaultTargetFrameworks` and `CurrentLatestFramework` in `Directory.Build.props` (every project, the samples, the tools and the `-windows` testbench derive from them) |
| SDK | `global.json` |
| CI | the `Install SDK OLD.0.x` steps (`dotnet-version: 'OLD.0.x'`) in every workflow under `.github/workflows`, `release.yml` several times. Renovate leaves these alone on purpose |
| Renovate holds | the three `allowedVersions: "/^OLD\\./"` rules in `.github/renovate.json5` (runtime, Serilog.Extensions.\*, sdk) and the comments that name `OLD` |
| Roslyn bound | the `allowedVersions` of the roslyn rule in `.github/renovate.json5`. It names a Roslyn version, so the grep doesn't find it |
| Docker images | the `mcr.microsoft.com/dotnet/sdk:OLD.0` and `aspnet:OLD.0` images in the `tests/extended` Dockerfiles, the default in `KafkaFixture.cs`, `tests/extended/README.md` and `AGENTS.md`. Renovate doesn't update Docker images |
| Docs | `docs/guides/quickstart.md` (SDK prerequisite), `docs/performance.md`. The migration guides of past majors also name `OLD`, because they describe that major's own target |
| Agent guidance | `AGENTS.md` (target framework, Renovate holds) and the build output paths (`bin/Release/netOLD.0`) in `.claude/skills`. A `lib\netOLD.0` path points into a third-party package (for example Confluent's XML docs) and changes only if that package ships the `netNEW.0` folder |

Leave `docs/performance.md` as is unless the benchmarks are rerun on `NEW`, and ask. Leave the released changelog chapters as they
are.

Done when every hit of the grep is assigned to a step below or explicitly left as is.

## 3. Retarget and bump the SDK

- `Directory.Build.props`: `netNEW.0` in both properties.
- `global.json`: the SDK version from step 1, keeping `rollForward: latestFeature`.
- Workflows: `dotnet-version: 'NEW.0.x'` and the step names.

Done when `Directory.Build.props`, `global.json` and every `setup-dotnet` step name `NEW`.

## 4. Bump the packages and lift the holds

- In the three `Directory.Packages.props` files (root, `samples`, `tests/extended`), update to the latest `NEW.x` version every package that the Renovate rules
  hold on `OLD` (the runtime group, `Serilog.Extensions.*` and the sdk group, matched by the `matchPackageNames` patterns in
  `.github/renovate.json5`). Read the versions from NuGet (`https://api.nuget.org/v3-flatcontainer/<lowercase id>/index.json`)
  and pick the latest stable one.
- `Microsoft.CodeAnalysis.NetAnalyzers` and `Microsoft.SourceLink.GitHub` ship with the SDK: take the highest stable `NEW.0.x`
  that isn't newer than the SDK in `global.json`. SourceLink skips some SDK versions (there is no 10.0.100), so its version can
  be lower than the SDK's.
- The third-party held packages (Npgsql, `Npgsql.EntityFrameworkCore.PostgreSQL`, `Serilog.Extensions.*`) ship their `NEW.0`
  some days or weeks after .NET. If one isn't out yet, stop and ask the user:
  - `Serilog.Extensions.*` can stay on `OLD`. With the lifted hold, Renovate proposes the set as one major PR once it ships
    (the grouping rules at the end of `.github/renovate.json5`).
  - `Npgsql.EntityFrameworkCore.PostgreSQL` caps EF Core below its next major, so it can't stay on `OLD` while EF Core moves,
    and it must move together with Npgsql. Either wait for it, or keep the whole set (`Npgsql*` and
    `Microsoft.EntityFrameworkCore*`) on `OLD`, Npgsql included even if its `NEW` is out. In the second case, add a temporary
    rule in `.github/renovate.json5` that holds `Npgsql*` and `Microsoft.EntityFrameworkCore*` on `OLD`. Place it right after
    the runtime rule (later rules win), comment it with "remove once `Npgsql.EntityFrameworkCore.PostgreSQL` NEW.x is out",
    and ask the user to track its removal (for example with an issue). Once it's removed, Renovate proposes the set as one
    major PR.
- Roslyn (`Microsoft.CodeAnalysis.CSharp`, `Microsoft.CodeAnalysis.BannedApiAnalyzers`): the LogEvents generator fails with
  CS9057 when Roslyn is newer than the compiler of the SDK. Read that compiler's version from the product version of
  `<dotnet root>/sdk/<SDK version>/Roslyn/bincore/Microsoft.CodeAnalysis.CSharp.dll`, and set the `allowedVersions` of the
  roslyn rule to allow up to that major and minor. Rewrite the rule's comments for the new SDK band and compiler version (the
  plain `OLD` to `NEW` replacement below would leave them wrong). Bump the two packages only if the user asks (otherwise Renovate proposes
  them), and confirm the version with the build in step 6.
- `.github/renovate.json5`: change the three `allowedVersions` to `"/^NEW\\./"` and replace `OLD` with `NEW` in the comments.

Done when no held package is left on `OLD` in the three props files, except the ones the user agreed to leave, the Renovate
holds name `NEW` and the Roslyn bound matches the new compiler.

## 5. Docker images, docs and agent guidance

Update every remaining hit from the inventory to `NEW`. In the docs, change only the statements of the current version. The
migration guides of past majors describe their own upgrade and stay as they are (the new target goes in the new guide, step 7).

Done when the inventory grep returns only the hits you deliberately kept.

## 6. Build, analyze and test

1. `dotnet build Silverback.slnx -c Release -warnaserror`. The new SDK enables new analyzer rules (`AnalysisMode=All`,
   `EnforceCodeStyleInBuild`) and the new C# version (`LangVersion latest`) brings new suggestions that become errors. Fix them,
   or suppress them in `.editorconfig` with the user's agreement when a rule doesn't fit the code base. Ask before any change to
   the public API.
2. The samples and the extended solution reference the `Silverback.*` packages at `$(BaseVersion)`, which the repository's
   `nuget.config` finds in `nuget/`. Run `pwsh ./nuget/pack.ps1` first, then
   `dotnet build samples/Silverback.Samples.slnx -c Release` and
   `dotnet build tests/extended/Silverback.Tests.Extended.slnx -c Release -warnaserror`, as `other-projects.yml` does in CI.
3. From `docs/`, run `pwsh ./build.ps1 -NoServe`. CI builds the docs only on release, and docfx loads the retargeted projects
   with the new SDK. If it fails, bump `docfx` in `.config/dotnet-tools.json`.
4. `dotnet jb inspectcode Silverback.slnx --no-build --severity=WARNING --format=Text --output=<report>`, with the report in the
   operating system's temporary directory (solution-wide, unlike the per-file check in `AGENTS.md`). If the ReSharper CLI doesn't support the new SDK yet, bump
   `jetbrains.resharper.globaltools` in `.config/dotnet-tools.json`. The change must leave no findings.
5. `dotnet test --solution Silverback.slnx -c Release --no-build` (the `Dependency=Docker` tests need Docker).
6. Offer the user the extended integration tests (`tests/extended/README.md`). They pull the new SDK image and take a long time,
   so run them only if the user accepts.

Done when everything builds without warnings, the docs build, the inspection has no findings and the tests pass.

## 7. Changelog and commit

- In the chapter of the version agreed in step 1, add under `### Breaking Changes` the line
  `* Target .NET NEW (drop .NET OLD)` and, under `### What's New`, the notable new package majors (for example EF Core NEW) if the
  user wants them listed.
- Describe the target change in the migration guide of the version agreed in step 1 (for a new major,
  `docs/guides/migration-v<major>.md`). If that guide doesn't exist yet, ask whether to create it. A new guide also goes in
  `docs/guides/toc.yml` (next to the other migration guides) and, if the user wants, in the cards of `docs/index.md`. Then rerun
  `pwsh ./build.ps1 -NoServe` from `docs/`.
- Commit as `feat!: target .NET NEW` (the breaking marker, because users must retarget too), after the user approves.

Done when the changelog entry and the migration guide are in place and the commit is approved.

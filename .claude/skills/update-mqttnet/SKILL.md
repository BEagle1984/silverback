# Upgrade MQTTnet

Silverback wraps the MQTTnet options classes (`MqttClientOptions`, `MqttClientTcpOptions`, `MqttClientWebSocketOptions`, `MqttClientTlsOptions`, `MqttClientWebSocketProxyOptions`) in its own records, and builds them with hand-written fluent builders. The generator `tools/Silverback.Tools.Generators.MqttConfigProxies` produces the record properties and, for the few MQTTnet `MqttClientOptionsBuilder` methods that Silverback forwards unchanged, partial builder method declarations, all into one `_autogenerated.cs`. The property summaries are not taken from MQTTnet: they are hardcoded in the generator's `DocumentationProvider.cs`.

Unlike the Kafka builders, most MQTT builder methods are hand-written with their own API names (`LimitPacketSize` sets `MaximumPacketSize`, `SendKeepAlive` and `DisableKeepAlive` set `KeepAlivePeriod`, `RequestCleanSession` sets `CleanSession`). A generated property is therefore not reachable from the fluent API until a builder method sets it.

Run everything from the repository root in Git Bash. Work on `main` unless told otherwise. Ask the user when a decision is not covered here (for example whether to expose a new option or to ignore it).

## Files involved

| What | Where |
| --- | --- |
| Package version | `Directory.Packages.props` (`MQTTnet`, four-part version such as `5.2.0.1603`) |
| Generator | `tools/Silverback.Tools.Generators.MqttConfigProxies`: `Program.cs` (the proxied types), `ProxyClassGenerator.cs` (properties), `BuilderGenerator.cs` (partial builder methods), `TypesMapper.cs` (proxy names and types that need mapping), `State.cs` (type queue) |
| Summaries | `DocumentationProvider.cs` in the generator, one `switch` per options class |
| Excluded properties | The `Where` filters in `ProxyClassGenerator.GetProxiedTypeProperties`, and the `[Obsolete]` MQTTnet properties (dropped by `ReflectionHelper.GetProperties` in `tools/Silverback.Tools.Generators.Common`). | Excluded builder methods | `BuilderGenerator.MustIgnore`: the `MqttClientOptionsBuilder` methods that Silverback replaces with its own API. Every other method becomes a generated `public partial` declaration |
| Generated code | `src/Silverback.Integration.MQTT/Messaging/Configuration/Mqtt/_autogenerated.cs` (five records, plus the partial declarations in `MqttClientConfigurationBuilder` and `MqttClientsConfigurationBuilder`) |
| Hand-written records | The excluded properties and the mapping to the MQTTnet type (`MapCore` is generated, the rest is hand-written). `MqttClientConfiguration.cs`: `ClientId`, `ProtocolVersion`, `UserProperties`, `ChannelOptions` as `Channel`. `MqttLastWillMessageConfiguration.cs`: the `Will*` options, renamed (`WillDelayInterval` as `Delay`, `WillMessageExpiryInterval` as `Expiration`, the others without the prefix), mapped in `MapToMqttNetType`; builder `MqttLastWillMessageConfigurationBuilder`1.cs`. `MqttClientTlsConfiguration.cs`: `ApplicationProtocols`, `CipherSuitesPolicy`, `EncryptionPolicy`, `AllowRenegotiation`, `TrustChain`. `MqttClientChannelConfiguration.cs`: `Tls` (the `TlsOptions` of the TCP and WebSocket options), mapped in `MqttClientTcpConfiguration.cs` and `MqttClientWebSocketConfiguration.cs`, which also declares `Proxy` (`ProxyOptions`) |
| Builders | `MqttClientConfigurationBuilder.cs` (`MqttClientOptions` settings), `MqttClientsConfigurationBuilder.cs` (the same methods for all clients: each one queues `builder => builder.X(...)`), `MqttClientTcpConfigurationBuilder.cs`, `MqttClientTlsConfigurationBuilder.cs`, `MqttClientWebSocketConfigurationBuilder.cs`, `MqttClientWebSocketProxyConfigurationBuilder.cs` |
| Changelog | `docs/changelog/<major>00.md` |

## How a new MQTTnet option gets exposed

- **New property on one of the five options classes.** The generator adds it to the record (`{ get; init; }`, default taken from a `new` MQTTnet instance, mapped in `MapCore`) with an empty summary. Add the summary to `DocumentationProvider.cs`, then add a hand-written builder method that sets it with `_configuration = _configuration with { Property = value }` (`_tcpConfiguration`, `_tlsConfiguration`, ... in the other builders). A `MqttClientOptions` setting needs the method in both `MqttClientConfigurationBuilder` and `MqttClientsConfigurationBuilder`. Choose the API name the way the neighbors do: `With<Name>` for a value, an `Enable`/`Disable` pair for a boolean, a verb that fits the MQTT concept otherwise.
- **Property needing a Silverback proxy type:** add a `TypesMapper.GetMappedPropertyTypeString` entry. The property stays generated with the proxy type and `MapCore` maps it with `?.ToMqttNetType()`, so the proxy record must declare `internal <MqttNetType> ToMqttNetType()` (`MqttClientWebSocketProxyConfiguration` does it with `=> MapCore()`). None of the existing entries is used this way today: the channel, TLS and proxy entries match properties that the `Where` filters exclude and that are mapped by hand, while the credentials and last will entries match no MQTTnet 5 property (`Credentials` is an `IMqttClientCredentialsProvider`, generated as is, and the will is split into the `Will*` properties).
- **Property needing special handling:** add it to the `Where` filters of `ProxyClassGenerator`, declare it in the record's hand-written partial **and** map it by hand (`ToMqttNetType`, `MapToMqttNetType`, `GetMqttClientOptions`). Without the manual mapping it is silently never passed to MQTTnet.
- **New class-typed MQTTnet property.** `State` queues MQTTnet classes found in property types for generation, unless `TypesMapper.MustGenerate` returns `false`. To use the new record, add a `TypesMapper.GetMappedPropertyTypeString` entry, so that the parent property gets the proxy type and `MapCore` calls `?.ToMqttNetType()` (see the previous bullet), and give the record a hand-written partial with `internal <MqttNetType> ToMqttNetType()` (and a builder). It also needs a case in the top-level `switch (property.DeclaringType!.Name)` of `DocumentationProvider.AppendSummary` with its own switch method, and an entry in the `classes` list of `diff-library-docs.sh` and in the `for f in ...` list of the step 6 changed-defaults check. To keep the raw MQTTnet type instead, return `false` from `TypesMapper.MustGenerate`.
- **New method on MQTTnet's `MqttClientOptionsBuilder`.** If it is not in `BuilderGenerator.MustIgnore`, the generator emits a `public partial` declaration in both builders and the build fails (`CS8795`, no implementation) until each is implemented with its documentation, as `WithTimeout` and `WithEnhancedAuthentication` are. When the method only sets a property that a hand-written method already covers, or Silverback has no use for it, add it to `MustIgnore` instead.
- **Removed or renamed property or method.** Fix or delete the hand-written builder methods, `MustIgnore` and `Where` entries that reference it. First check in the MQTTnet source or `MQTTnet.xml` that it was not merely marked `[Obsolete]`: `ReflectionHelper.GetProperties` drops obsolete properties, so they vanish from the generated record (and the step 3 diff shows them as removed) while the library still has them. Don't delete public Silverback API in that case without asking the user. Options: keep the property hand-written and marked `[Obsolete]`, mapped manually with the warning suppressed, until the next major version.

## Steps

1. **Baseline.** Before touching the version, run `.claude/skills/update-mqttnet/regenerate.sh "$TEMP/mqtt-proxies-old"` and check that `git diff -- src/Silverback.Integration.MQTT/Messaging/Configuration/Mqtt/_autogenerated.cs` is empty. If it isn't, the generated file is stale: show the user the pending changes and ask whether to include them. Revert with `git checkout -- src/Silverback.Integration.MQTT/Messaging/Configuration/Mqtt/_autogenerated.cs` if they don't.

2. **Bump** `MQTTnet` in `Directory.Packages.props`. Read the release notes (`https://api.github.com/repos/dotnet/MQTTnet/releases/tags/v<version>`) for new or changed options and breaking changes. The 5.x release tags have three parts (`v5.2.0` for NuGet `5.2.0.1603`), the 4.x ones had four, so confirm the tag with `gh api repos/dotnet/MQTTnet/releases --jq '.[].tag_name'`.

3. **Regenerate**: `.claude/skills/update-mqttnet/regenerate.sh "$TEMP/mqtt-proxies-new"`. The script runs the generator, replaces everything below the hand-written file header (the part starting at the first `/// <content>`) and runs `dotnet jb cleanupcode` with the `Silverback: Full Cleanup` profile on the file.
   - If the generator no longer compiles, MQTTnet removed or renamed something it references. The build error names the stale reference (file and line): `CS0117` for a property referenced with `nameof(Class.Member)` (`DocumentationProvider.cs` cases, the `Where` filters), `CS0103`/`CS0246` for a type (`TypesMapper.cs`, `Program.cs`). Confirm it in the MQTTnet release notes or source (`diff-library-docs.sh` lists a property as `REMOVED` only if MQTTnet documented it, and many proxied properties have no XML docs), delete or rename the reference and run the script again. Stale `BuilderGenerator.MustIgnore` names are plain strings and cause no error: remove them when you notice them.
   - `diff "$TEMP/mqtt-proxies-old/mqtt.cs" "$TEMP/mqtt-proxies-new/mqtt.cs"` is the exact list of added, removed or retyped properties and partial builder methods. If it is empty no option was added, removed or retyped: skip step 4 and the fixes of step 5 (the build still has to pass). Steps 6 and 8 still run, because summaries and defaults change without signature changes.
   - Check the generator really used the new version: `bin/Release/net10.0/MQTTnet.dll` product version under the generator project.

4. **Expose new options** as described above, with tests for each new builder method in the existing `<Builder>Tests` class (see "Test organization" in `AGENTS.md`; both client builders for a `MqttClientOptions` setting), and document each new property in `DocumentationProvider.cs` (otherwise it gets an empty `<summary>`). Take the text from the MQTTnet XML docs, shown by `.claude/skills/update-mqttnet/diff-library-docs.sh <old-version> <new-version>` (`ADDED` entries; it comes from `MQTTnet.xml` in the NuGet global packages folder). Style:
   - Properties start with `Gets` (`Gets a value indicating whether` for booleans), builder methods with `Sets` (or `Enables`/`Disables`), the `<param>` with `The ...`.
   - Turn backticks into `<c>...</c>`, references to other settings into `<see cref="OtherProperty" />`, and use the full namespace for MQTTnet types (`<see cref="MQTTnet.Formatter.MqttProtocolVersion.V500" />`).
   - Mind the difference between the property and the builder method: a builder method documents what it does with its own name and parameters, and must stay accurate when it sets a differently named or differently typed property.
   Then run `regenerate.sh` again.

5. **Build**: `dotnet build Silverback.slnx -c Release -warnaserror`. Expected findings:
   - `CS8795` (partial method without implementation): a new forwarded `MqttClientOptionsBuilder` method. Implement the documented method in both builders, or add it to `BuilderGenerator.MustIgnore` and regenerate. If the method is `[Obsolete]` in MQTTnet (obsolete methods are not filtered), add it to `MustIgnore` instead of implementing it.
   - `CS0759` (partial implementation without declaration): a forwarded `MqttClientOptionsBuilder` method was removed or its signature changed (marking it `[Obsolete]` doesn't cause this, since obsolete methods are still generated). Ask the user whether to keep the public Silverback method as a hand-written, non-partial method (for example `[Obsolete]` until the next major version) or to remove it.
   - Errors in hand-written code that references a removed, renamed or retyped MQTTnet member: fix it, ask if the impact on the public API is unclear.
   - New obsolete warnings (`CS0618`) from MQTTnet APIs used by hand-written code: replace the usage when MQTTnet offers an equivalent. Obsolete properties are never generated. If the obsolete member backs a public Silverback setting (the hand-written mappings in `GetMqttClientOptions`, `MapToMqttNetType`, `ToMqttNetType`), don't drop the mapping, or the setting is silently never passed to MQTTnet: keep it with a scoped `#pragma warning disable CS0618` and ask the user whether to mark the Silverback property and its builder methods `[Obsolete]` until the next major version.

6. **Check the summaries.** There is no scripted builder-versus-property check here, because the builder method names and semantics differ from the properties.
   - Run `.claude/skills/update-mqttnet/diff-library-docs.sh <old-version> <new-version>` and settle every entry against its `silverback:` line. `CHANGED`: if the meaning changed, update the `DocumentationProvider.cs` entry (reworded text needs nothing; `delta` shows the changed words). `REMOVED` means the XML doc entry is gone. If step 3 broke the generator build, the property was removed: delete its case. If the case still compiles, the property still exists and MQTTnet only dropped its docs: keep the case. `ADDED` or `CHANGED` with `silverback: none`: first check that the step 3 generator output declares it as a record property (`<Name> { get; init; }`; `DocumentationProvider.cs` only documents record properties, so a case for a property that is not generated is dead). If it is not generated, it is an `[Obsolete]` MQTTnet property (nothing to document) or excluded by a `Where` filter. If it is generated, document it. If a `Where` filter excludes it, it is usually still exposed by hand under the same or another name: find the mapping (`grep -n "options\.<Property>\b\|\.<Property> =" src/Silverback.Integration.MQTT/Messaging/Configuration/Mqtt/*.cs`, then read the mapping code to see which record property it reads) and review the docs of that record property and of the builder methods that set it. Properties without XML docs in MQTTnet are not covered: the generator diff of step 3 is the only signal for them.
   - For each reported property, find the builder methods that set it: `grep -ni "<Property>" src/Silverback.Integration.MQTT/Messaging/Configuration/Mqtt/*Builder*.cs`. Some methods set a backing field that `Build()` copies into the record (`WithSessionExpiration`, `RequestPersistentSession` and `RequestCleanSession` assign `_sessionExpiryInterval`), and `with` blocks span several lines, so also grep the field names and follow each field to the methods that assign it. The `MqttClientConfigurationBuilder` and `MqttClientsConfigurationBuilder` methods are twins. Review each method's summary, `<param>` and `<remarks>` against the new library text and update them when the behavior, the default or the valid range changed. Also grep the guides in `docs/guides` for the property or method name.
   - **Changed defaults.** MQTTnet's XML docs rarely state defaults, but many Silverback summaries do ("The default is 15 seconds"), taken from the MQTTnet initializers (`new MqttClientOptions()` and the like), so a changed initializer shows up in neither diff. Diff the five options classes between the two release tags, one file at a time (the compare API truncates its file list at 300 files, so it silently misses them on larger upgrades): `for f in MqttClientOptions MqttClientTcpOptions MqttClientWebSocketOptions MqttClientTlsOptions MqttClientWebSocketProxyOptions; do echo "== $f"; diff <(gh api "repos/dotnet/MQTTnet/contents/Source/MQTTnet/Options/$f.cs?ref=v<old>" -H "Accept: application/vnd.github.raw") <(gh api "repos/dotnet/MQTTnet/contents/Source/MQTTnet/Options/$f.cs?ref=v<new>" -H "Accept: application/vnd.github.raw"); done`, and read the changed `= value` initializers. For each one, verify the "The default is" statements in `DocumentationProvider.cs` and in the builder docs, and the guides.

7. **Test**: `dotnet test --solution Silverback.slnx -c Release --no-build` (the `Dependency=Docker` tests start their own PostgreSQL containers and need only a running Docker; without Docker add `--filter "Dependency!=Docker"`). Then offer the user the extended MQTT integration tests (`tests/extended/README.md`, `--filter "Type=Integration&Broker=MQTT"`, see "Running tests" in `AGENTS.md`); run them only if they accept, and run them once, without editing files meanwhile. Keep the log until you have read it, then delete the TRX files and the `tests/extended/artifacts` folders created by passing runs.

8. **Changelog**: in the topmost section of the current major version changelog, update (or add, under `### What's New`) the line `* Upgrade to [MQTTnet <version>](https://github.com/dotnet/MQTTnet/releases/tag/v<version>)`, where `<version>` is the release tag version (`5.2.0`, not the four-part NuGet version; 4.x entries used four parts because their tags did), and add a line for newly exposed options. If the topmost changelog version, `<silverback-version>`, is already released (`git tag -l v<silverback-version>`), ask the user which version to add (the `BaseVersion` in `Directory.Build.props` may need a bump too).

9. **Commit** as `feat: upgrade to MQTTnet <version>`.

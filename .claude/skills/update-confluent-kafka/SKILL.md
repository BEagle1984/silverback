# Upgrade Confluent.Kafka

Silverback wraps the Confluent configuration classes (`ClientConfig`, `ConsumerConfig`, `ProducerConfig`, `SchemaRegistryConfig` and the Avro, JSON and Protobuf serializer and deserializer configs) in its own records and builders. Most of that code is generated by `tools/Silverback.Tools.Generators.KafkaConfigProxies` into two `_autogenerated.cs` files. The summaries are not taken from Confluent: they are hardcoded in the generator's `DocumentationProvider.cs`. The public builder methods are `partial`: the implementation is generated, while the documented defining declaration is hand-written.

Run everything from the repository root in Git Bash. Work on `main` unless told otherwise. Ask the user when a decision is not covered here (for example whether to expose a new setting or to ignore it).

## Files involved

| What | Where |
| --- | --- |
| Package versions | `Directory.Packages.props` (`Confluent.Kafka` and all `Confluent.SchemaRegistry*`, always the same version) |
| Generator | `tools/Silverback.Tools.Generators.KafkaConfigProxies` (`Program.cs`, `--schemaregistry` for the schema registry part). When a config class is added to `Program.cs` (or the settings move to a new Confluent base class), also add a case to the top-level `switch (property.DeclaringType!.Name)` of `DocumentationProvider.AppendSummary` with its own `AppendSummaryFor<Class>` method (named after the class: `diff-library-docs.sh` matches the sections by that name), and add the class to the `classes` and `packages` lists of `diff-library-docs.sh` |
| Summaries | `DocumentationProvider.cs` in the generator, one `switch` per Confluent config class (the serde configs share one for the serializers, one for the deserializers and one for `SerdeConfig`) |
| Excluded settings | Not proxied at all: `IgnoredProperties.cs` and the `[Obsolete]` Confluent properties (dropped by `ReflectionHelper.GetProperties` in `tools/Silverback.Tools.Generators.Common`). Record property only: the `GroupId` filter in `ProxyClassGenerator` (the property is hand-written in `KafkaConsumerConfiguration.cs`, while `WithGroupId` is still generated, with a hand-written declaration). Proxied with an `internal` builder method (no declaration needed): the `MustBeInternal` lists in `ParentBuilderGenerator`, `BuilderGenerator`, `SchemaRegistryBuilderGenerator` and `SerdeBuilderGenerator`. Boolean settings go there and get hand-written `Enable…`/`Disable…` methods. `ParentBuilderGenerator.IsObsolete` lists the public client builder methods marked `[Obsolete]` in their declaration |
| Generated code | `src/Silverback.Integration.Kafka/Messaging/Configuration/Kafka/_autogenerated.cs` and `src/Silverback.Integration.Kafka.SchemaRegistry/Messaging/Configuration/Kafka/SchemaRegistry/_autogenerated.cs` |
| Builder declarations | `ClientConfig` settings: `KafkaClientConfigurationBuilder`1.cs` **and** `KafkaClientsConfigurationBuilder.cs`; `ConsumerConfig`: `KafkaConsumerConfigurationBuilder.cs`; `ProducerConfig`: `KafkaProducerConfigurationBuilder.cs`; `SchemaRegistryConfig`: `KafkaSchemaRegistryConfigurationBuilder.cs`; serde configs: `Kafka<Format><Serializer\|Deserializer>ConfigurationBuilder.cs` next to it |
| Changelog | `docs/changelog/<major>00.md` |

The serializer/deserializer configs (`AvroSerializerConfig`, `JsonDeserializerConfig`, ...) are generated by `SerdeProxyClassGenerator`/`SerdeBuilderGenerator`, flattening the inherited `SerdeConfig` settings into each record. Their dictionaries are exposed as `IReadOnlyDictionary` and their non-nullable values as nullable, so that only the configured settings are mapped. A setting shared by several serde configs needs a declaration in each builder.

## Steps

1. **Baseline.** Before touching the versions, run `.claude/skills/update-confluent-kafka/regenerate.sh "$TEMP/kafka-proxies-old"` and check that `git diff -- 'src/Silverback.Integration.Kafka*/**/_autogenerated.cs'` is empty. If it isn't, the generated files are stale (it happened with the schema registry file, last regenerated for 2.8.0): show the user the pending settings and ask whether to include them. Revert with `git checkout -- 'src/Silverback.Integration.Kafka*/**/_autogenerated.cs'` if they don't.

2. **Bump** `Confluent.Kafka` and every `Confluent.SchemaRegistry*` in `Directory.Packages.props` to the new version. Read the release notes (`https://api.github.com/repos/confluentinc/confluent-kafka-dotnet/releases/tags/v<version>`) and the linked librdkafka notes for new or changed configuration properties.

3. **Regenerate**: `.claude/skills/update-confluent-kafka/regenerate.sh "$TEMP/kafka-proxies-new"`. The script runs the generator, replaces everything below the hand-written file header (the part starting at the first `/// <content>`) and runs `dotnet jb cleanupcode` with the `Silverback: Full Cleanup` profile on both files. It is equivalent to pasting the generator output into the files and running the full cleanup in Rider.
   - If the generator no longer compiles, the build error names the stale reference to a removed or renamed Confluent member (file and line, usually a `DocumentationProvider.cs` case, `CS0117`). Confirm it in the release notes (`diff-library-docs.sh` lists it as `REMOVED` only if Confluent documented it). Delete or rename a `DocumentationProvider.cs` case; ask the user before dropping special handling in another generator file (`ParentProxyClassGenerator`, `ParentBuilderGenerator`, `ProxyClassGenerator`). Then run the script again.
   - `diff "$TEMP/kafka-proxies-old/kafka.cs" "$TEMP/kafka-proxies-new/kafka.cs"` (and `schema-registry.cs`) is the exact list of added, removed or retyped settings. If it is empty no setting was added, removed or retyped (2.16.0 was such a release for the Kafka config): skip step 4 and the fixes of step 5 (the build still has to pass). Steps 6 and 8 still run, because summaries and defaults change without signature changes.
   - Check the generator really used the new version: `bin/Release/net10.0/Confluent.Kafka.dll` product version under the generator project.

4. **Document new settings** in `DocumentationProvider.cs` (new settings otherwise get an empty `<summary>`). Run `.claude/skills/update-confluent-kafka/diff-library-docs.sh <old-version> <new-version>`: each `ADDED` entry shows the Confluent text to adapt (it comes from the XML docs in the NuGet global packages folder, members `P:Confluent.Kafka.ConsumerConfig.<Name>` and so on). Style:
   - Properties start with `Gets` (`Gets a value indicating whether` for booleans), builder methods with `Sets`, the `<param>` with `The ...`.
   - Turn backticks into `<c>...</c>` and references to other settings into `<see cref="OtherProperty" />` (property) / `<see cref="WithOtherProperty" />` (builder); use the full namespace for Confluent types (`<see cref="Confluent.Kafka.Acks.All" />`).
   - Drop the `default:`/`importance:` lines unless the default is useful; wrap lines like the neighboring entries.
   Then run `regenerate.sh` again.

5. **Build**: `dotnet build Silverback.slnx -c Release -warnaserror`. Expected findings:
   - `CS0759` (no defining declaration for a partial method): add the documented declaration to the builder file listed above, in the same order the generator emits the methods, mirroring the property summary. `ClientConfig` settings need it in both client builders. A URL setting needs `[SuppressMessage("Design", "CA1054:URI-like parameters should not be strings", Justification = "Declared as string in the underlying library")]`.
   - A declaration without implementation: the setting was removed or renamed in Confluent, or only marked `[Obsolete]` (obsolete properties are no longer generated, so the setting is gone from the step 3 diff although `diff-library-docs.sh` doesn't report it `REMOVED`). Check the Confluent XML docs or source first. If it is only obsolete, don't remove the public declaration without asking the user; options: keep it hand-written, marked `[Obsolete]`, mapped manually with the warning suppressed, until the next major version. Otherwise remove or rename the declaration.
   - Anything else in hand-written code (e.g. an enum or type change): fix it, ask if the impact on the public API is unclear.

6. **Check the summaries.**
   - Run `.claude/skills/update-confluent-kafka/diff-library-docs.sh <old-version> <new-version>` (step 4 already did) and settle every entry against its `silverback:` line. `CHANGED`: if the meaning changed, update the `DocumentationProvider.cs` entry and the matching builder declarations (reworded text needs nothing; `delta` shows the changed words). `REMOVED` means the XML doc entry is gone. If step 3 broke the generator build, the property was removed: delete its case. If the case still compiles, the property still exists: if it moved to a base class (an `ADDED` entry there), move the case to that section; if it is still generated in the same class, keep the case (Confluent only dropped its docs). `ADDED` or `CHANGED` with `silverback: none`: first check that the step 3 generator output declares it as a record property (`<Name> { get; init; }`; a builder method alone doesn't count, `DocumentationProvider.cs` only documents record properties). If it doesn't, it is not generated and a `DocumentationProvider.cs` case would be dead. An `[Obsolete]` Confluent setting needs nothing (for example `SchemaRegistryConfig.KeySubjectNameStrategy`/`ValueSubjectNameStrategy`). A setting excluded by `IgnoredProperties.cs` or the `GroupId` filter may still be exposed by hand (today `GroupId` and `EnableAutoCommit`): find the mapping with `grep -rn "confluentConfig\.<Name>\b" src/Silverback.Integration.Kafka*/Messaging/Configuration/Kafka` and review the docs of the record property and of the builder methods that set it. If it is generated, document it. For a setting in a `MustBeInternal` list there is no public `With<Name>` declaration, and `check-summaries.sh` does not cover the hand-written public methods (`EnableIdempotence()`/`DisableIdempotence()`, `EnableTransactions(string)`, ...): on `CHANGED`, find them with `grep -rn "With<Name>(" src/Silverback.Integration.Kafka*/Messaging/Configuration/Kafka --include="*Builder*.cs"` and review their docs.
   - Run `.claude/skills/update-confluent-kafka/check-summaries.sh`: it lists the builder methods whose summary doesn't match the property summary (copy-paste errors). `IsolationLevel` is a known, harmless wording difference. Spot-check any new or changed entry against the Confluent text.

7. **Test**: `dotnet test --solution Silverback.slnx -c Release --no-build` (the `Dependency=Docker` tests start their own PostgreSQL containers and need only a running Docker; without Docker add `--filter "Dependency!=Docker"`). Then offer the user the extended Kafka integration tests (`tests/extended/README.md`, over 12 minutes, see "Running tests" in `AGENTS.md`); run them only if they accept, and run them once, without editing files meanwhile. Keep the log until you have read it, then delete the TRX files and the `tests/extended/artifacts` folders created by passing runs.

8. **Changelog**: in the topmost section of the current major version changelog, update (or add, under `### What's New`) the line `* Upgrade to [Confluent.Kafka <version>](https://github.com/confluentinc/confluent-kafka-dotnet/releases/tag/v<version>)` and add a line for newly exposed settings. If the topmost changelog version, `<silverback-version>`, is already released (`git tag -l v<silverback-version>`), ask the user which version to add (the `BaseVersion` in `Directory.Build.props` may need a bump too).

9. **Commit** as `feat: upgrade to Confluent.Kafka <version>`.

# Upgrade Confluent.Kafka

Silverback wraps the Confluent configuration classes (`ClientConfig`, `ConsumerConfig`, `ProducerConfig`, `SchemaRegistryConfig` and the Avro, JSON and Protobuf serializer and deserializer configs) in its own records and builders. Most of that code is generated by `tools/Silverback.Tools.Generators.KafkaConfigProxies` into two `_autogenerated.cs` files. The summaries are not taken from Confluent: they are hardcoded in the generator's `DocumentationProvider.cs`. The public builder methods are `partial`: the implementation is generated, while the documented defining declaration is hand-written.

Run everything from the repository root in Git Bash. Work on `master` unless told otherwise. Ask the user when a decision is not covered here (for example whether to expose a new setting or to ignore it).

## Files involved

| What | Where |
| --- | --- |
| Package versions | `Directory.Packages.props` (`Confluent.Kafka` and all `Confluent.SchemaRegistry*`, always the same version) |
| Generator | `tools/Silverback.Tools.Generators.KafkaConfigProxies` (`Program.cs`, `--schemaregistry` for the schema registry part) |
| Summaries | `DocumentationProvider.cs` in the generator, one `switch` per Confluent config class (the serde configs share one for the serializers, one for the deserializers and one for `SerdeConfig`) |
| Excluded settings | `IgnoredProperties.cs` (not proxied at all) and the `MustBeInternal` lists in `ParentBuilderGenerator`, `BuilderGenerator`, `SchemaRegistryBuilderGenerator` and `SerdeBuilderGenerator` (proxied, builder method `internal`, no declaration needed). Boolean settings go there and get hand-written `Enable…`/`Disable…` methods. `ParentBuilderGenerator.IsObsolete` lists the public client builder methods marked `[Obsolete]` in their declaration |
| Generated code | `src/Silverback.Integration.Kafka/Messaging/Configuration/Kafka/_autogenerated.cs` and `src/Silverback.Integration.Kafka.SchemaRegistry/Messaging/Configuration/Kafka/SchemaRegistry/_autogenerated.cs` |
| Builder declarations | `ClientConfig` settings: `KafkaClientConfigurationBuilder`1.cs` **and** `KafkaClientsConfigurationBuilder.cs`; `ConsumerConfig`: `KafkaConsumerConfigurationBuilder.cs`; `ProducerConfig`: `KafkaProducerConfigurationBuilder.cs`; `SchemaRegistryConfig`: `KafkaSchemaRegistryConfigurationBuilder.cs`; serde configs: `Kafka<Format><Serializer\|Deserializer>ConfigurationBuilder.cs` next to it |
| Changelog | `docs/changelog/<major>00.md` |

The serializer/deserializer configs (`AvroSerializerConfig`, `JsonDeserializerConfig`, ...) are generated by `SerdeProxyClassGenerator`/`SerdeBuilderGenerator`, flattening the inherited `SerdeConfig` settings into each record. Their dictionaries are exposed as `IReadOnlyDictionary` and their non-nullable values as nullable, so that only the configured settings are mapped. A setting shared by several serde configs needs a declaration in each builder.

## Steps

1. **Baseline.** Before touching the versions, run `.claude/skills/update-confluent-kafka/regenerate.sh "$TEMP/kafka-proxies-old"` and check that `git diff` is empty. If it isn't, the generated files are stale (it happened with the schema registry file, last regenerated for 2.8.0): show the user the pending settings and ask whether to include them. Revert with `git checkout -- '*/_autogenerated.cs'` if they don't.

2. **Bump** `Confluent.Kafka` and every `Confluent.SchemaRegistry*` in `Directory.Packages.props` to the new version. Read the release notes (`https://api.github.com/repos/confluentinc/confluent-kafka-dotnet/releases/tags/v<version>`) and the linked librdkafka notes for new or changed configuration properties.

3. **Regenerate**: `.claude/skills/update-confluent-kafka/regenerate.sh "$TEMP/kafka-proxies-new"`. The script runs the generator, replaces everything below the hand-written file header (the part starting at the first `/// <content>`) and runs `dotnet jb cleanupcode` with the `Silverback: Full Cleanup` profile on both files. It is equivalent to pasting the generator output into the files and running the full cleanup in Rider.
   - `diff "$TEMP/kafka-proxies-old/kafka.cs" "$TEMP/kafka-proxies-new/kafka.cs"` (and `schema-registry.cs`) is the exact list of added, removed or retyped settings. If it is empty the upgrade is just the version bump plus the changelog (2.16.0 was such a release for the Kafka config).
   - Check the generator really used the new version: `bin/Release/net10.0/Confluent.Kafka.dll` product version under the generator project.

4. **Document new settings** in `DocumentationProvider.cs` (new settings otherwise get an empty `<summary>`). Take the text from the Confluent XML docs, located under the NuGet global packages folder (`dotnet nuget locals global-packages -l`, e.g. `D:\.nuget\packages\confluent.kafka\<version>\lib\net10.0\Confluent.Kafka.xml`, members `P:Confluent.Kafka.ConsumerConfig.<Name>`; same for `confluent.schemaregistry` / `SchemaRegistryConfig` and the `confluent.schemaregistry.serdes.*` packages). Style:
   - Properties start with `Gets` (`Gets a value indicating whether` for booleans), builder methods with `Sets`, the `<param>` with `The ...`.
   - Turn backticks into `<c>...</c>` and references to other settings into `<see cref="OtherProperty" />` (property) / `<see cref="WithOtherProperty" />` (builder); use the full namespace for Confluent types (`<see cref="Confluent.Kafka.Acks.All" />`).
   - Drop the `default:`/`importance:` lines unless the default is useful; wrap lines like the neighboring entries.
   Then run `regenerate.sh` again.

5. **Build**: `dotnet build Silverback.sln -c Release -warnaserror`. Expected findings:
   - `CS0759` (no defining declaration for a partial method): add the documented declaration to the builder file listed above, in the same order the generator emits the methods, mirroring the property summary. `ClientConfig` settings need it in both client builders. A URL setting needs `[SuppressMessage("Design", "CA1054:URI-like parameters should not be strings", Justification = "Declared as string in the underlying library")]`.
   - A declaration without implementation: the setting was removed or renamed in Confluent; remove or rename the declaration.
   - Anything else in hand-written code (e.g. an enum or type change): fix it, ask if the impact on the public API is unclear.

6. **Check the summaries.**
   - Diff the Confluent XML docs of the config classes between the old and new version to spot changed descriptions:
     `diff <(ext old.xml) <(ext new.xml)` with `ext() { tr -d '\r' < "$1" | awk '/<member name="P:Confluent\.(Kafka|SchemaRegistry)\.[A-Za-z]*Config\./{f=1} f{print} /<\/member>/{f=0}'; }`. Update the affected `DocumentationProvider.cs` entries and builder declarations.
   - Run `.claude/skills/update-confluent-kafka/check-summaries.sh`: it lists the builder methods whose summary doesn't match the property summary (copy-paste errors). `IsolationLevel` is a known, harmless wording difference. Spot-check any new or changed entry against the Confluent text.

7. **Test**: `dotnet test Silverback.sln -c Release --no-build` (the Docker-dependent tests need the root `docker-compose.yaml` stack running). Then offer the user the extended Kafka integration tests (`tests/extended/README.md`, over 12 minutes, see "Running tests" in `AGENTS.md`); run them only if they accept, and run them once, without editing files meanwhile. Keep the log until you have read it, then delete the TRX files and the `tests/extended/artifacts` folders created by passing runs.

8. **Changelog**: in the topmost section of the current major version changelog, update (or add, under `### What's New`) the line `* Upgrade to [Confluent.Kafka <version>](https://github.com/confluentinc/confluent-kafka-dotnet/releases/tag/v<version>)` and add a line for newly exposed settings. If the topmost version is already released (`git tag -l v<version>`), ask the user which version to add (the `BaseVersion` in `Directory.Build.props` may need a bump too).

9. **Commit** as `feat: upgrade to Confluent.Kafka <version>`.
